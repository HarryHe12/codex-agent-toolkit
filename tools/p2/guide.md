# P2 行为验收

沿用 P1 的安装方式。采用 P2 的项目可以在工作区添加 `.agent-toolkit/acceptance.json`，把关键行为交给实际示例和回归验证。没有这份配置的项目按原有流程运行。

## 声明需要验证的行为

配置可以从包内 `examples/acceptance.json` 起步。每个场景使用独立的 `id`，指定输入文件、业务文档和要执行的业务示例。输入使用相对工作区的普通文件路径，包含示例与测试实际依赖的源码、脚本和夹具。避免依赖被忽略的本地状态。

- `document` 保存现行业务说明。`behavior` 写明可观察的业务规则。文档必须包含它，并在单独的 `text` 代码块中列出 `example.output` 的实际预期。
- `example.argv` 运行正常的项目入口。验收要求程序成功退出，且实际标准输出精确匹配文档中的预期。
- `test` 可选。`test.argv` 指定回归命令，`test.success` 是成功时由该用例输出的独立一行。预期值来自业务规则、公开契约或独立计算。
- 关键场景可配置 `counterexample`。在新的临时副本里，将指定源码中恰好出现一次的 `before` 替换为 `after`，再运行同一个 `test.argv`。只有指定退出码和独立的错误标记同时出现，才证明测试能抓住该错误。超时、异常退出或其他报错都不能当作成功拒绝。

配置中的 `argv` 按参数数组执行。审阅项目计划和命令后，用 `--acceptance` 显式选择执行。临时副本只隔离工作区文件改写，例行代码检查、依赖准备和真实数据操作仍按项目流程。

## 运行与核对结果

按 P1 命令登记和编辑。先检查计划，并在 `verify` 的 `--` 之前加上 `--acceptance`，即可在原有项目验证后运行命中场景。例子、正常测试和反证分别使用干净副本。改动没有触及已声明场景时，输出 `not_applicable`。

成功记录绑定当前计划和命中场景的输入文件。更改相关文件后需要重新验证，才能获得收尾证据。结构化结果列出场景名、文档、示例、测试和反证状态。用它确认实际覆盖，再按业务范围判断是否还需要补充用例。

对于并发扣减、权限隔离或数据副作用，可把独立测试命令指向项目已有的隔离测试入口。P2 的一个代表性错误只能证明这一错误被抓住。业务审查、原生宿主验证和真正的交付收益仍各有证据。
