# Codex 工作流程优化：异机迁移实施指南

版本：2026-11-21 跨聊天整合版。面向其他使用者的 Codex，交付本文与 `Codex-优化整合源码包.zip`。源码位于压缩包的 `implementation/`。只讨论在接收方机器安装与实施，不要求原机器、原项目或历史聊天。合成复验材料位于 `validation/`，不属于安装目录。

## 1. 给接手 Codex 的任务

在用户指定的环境中落实本指南：先核实已安装组件并保全原状，复用合格实现，补齐缺口，验证本地即时拦截和修复后放行，最后报告实际结果。收到明确执行要求后继续做，不止输出建议。

本文不额外授权推送、合并、部署、迁移真实数据、扩大权限或代用户信任 Hooks；这些步骤按当前会话的明确授权执行。发送方的个人偏好和项目授权不属于迁移内容。

### 默认治理范围

必做范围是当前聊天所负责的本次新增和改写：检查新引入或加重的问题，并验证本次改动影响的行为。接手、登记根目录或结束聊天，都不自动授权治理既有内容。

既有代码、文档和历史聊天默认保留；全量审计、清理、重构及补齐历史缺口，仅在用户明确要求后按指定范围执行。无关的存量问题不得成为本次交付的强制修复项。

可按需读取相关旧内容、建立可核对的基线或进行查重，以判断本次改动的影响；读取或检测不等于获准修改历史。基线保留原有缺陷，不能把本次新增问题登记成存量；跨聊天延续同一未完成任务时，已引入的问题仍属于该任务。

本指南后文的安装、覆盖核验及历史治理步骤，按用户实际授权选择；不作为每个普通聊天的必做清单。历史测试、审计结论和待办只提供证据，不自动生成当前任务。

**目标流程：**

```text
代码：登记实际根目录 → 保存恢复点 → 编辑 → 本地同步检查 → 修复 → 业务验证 → 按授权提交
指令：确定唯一归属 → 暂存草稿 → 结构检查与语义对照 → 逐条审阅 → 原子写入 → 自动复查
规模化：先建立可信的单次修改与验证闭环，再扩大自主执行或并行数量
```

## 2. 优化原则及对应动作

| 原则 | 动作 | 证据 |
|---|---|---|
| 可执行约束 | ESLint、AST、模块禁用 | 违规自动失败 |
| 本地及时反馈 | 编辑后与结束前检查 | 真实失败和修复放行 |
| 唯一权威 | 归属明确、条件引用 | 新旧条目去向 |
| 管住新增 | 草稿预检、逐条审阅 | 过期审阅被拒绝 |
| 避免伪精简 | 同时查体积与复杂度 | 压成一行仍失败 |
| 可恢复 | 保全原状和业务含义 | 恢复点与业务回归 |

不追求 PR 数量、测试数量或文件行数本身。共同目标是更少返工、错误更早出现、需要人反复纠正的次数减少。

## 3. 异机安装流程

源码包中的版本已移除原用户绝对路径，解释器和位置由接收环境决定；它仍是需要审阅、配置和验收的参考实现，不是一键保证成功的安装器。

参考环境为 macOS/Linux、Node 24 与 Python 3.9+。实现使用 Unix 文件锁；Windows 必须另适配文件锁、命令和路径，并完成独立验收，不能直接宣称支持。

共享账户不构成文件已同步的证明。核对电脑、系统用户、CODEX_HOME、项目路径、Git 同步方式及文件哈希；未定义的文件名先确认位置和用途，不自动当作标准配置。

先按下面清单保全目标机器原状：检查各相关仓库的分支、HEAD、暂存、未暂存及需要保留的未跟踪文件；保存已有全局规则、Skill、Hook 和配置的可核对备份。敏感配置不进入 Git 或源码包。

将源码分别放到目标 `CODEX_HOME` 的 `code-guard/`、`md-governance/` 与 `skills/`，沿用其原有布局；未设置 `CODEX_HOME` 时才以 `~/.codex` 为基准。已有安装需做差异合并，不能整目录覆盖。

以下路径均相对接收方的 `CODEX_HOME`：

| 位置 | 内容 |
|---|---|
| `code-guard/` | 代码检查器及依赖锁 |
| `md-governance/` | 指令检查和受控写入 |
| `skills/` | 两个可条件加载的 Skill |
| `hooks.json` | 合并后的用户 Hook 配置 |

| 配置项 | 含义 |
|---|---|
| `CODEX_HOME` | 接收方的用户安装根目录 |
| `CODEX_GUARD_NODE` | 可选 Node 可执行路径，默认从 PATH 查找 |
| `CODEX_GUARD_PYTHON` | 可选 Python 路径；驱动默认传入自身解释器 |
| `CODEX_GUARD_MD_HOME` | 可选文档组件目录；默认与代码组件相邻 |

只合并接收方需要的 Skill 条件入口，保留其原有偏好和权限；五个 Skill 按任务加载，不每次全部展开，不将整份指南塞进常驻入口。

部署路径不同时核对以上配置及现有 Hook 数组；不要覆盖其他 Hooks 或重复注册。GUI 进程的 PATH 可能不同，注册时优先将模板中的 Python 命令替换为接收机器的准确绝对路径；确保它能找到 Node。不要复制发送方的依赖目录、私有状态或旧收据。

安装依赖使用源码包中的锁文件，不把目标项目的依赖、工具链或锁文件顺便改掉。以下命令仅在完成目录和解释器适配后执行：

```sh
cd /目标/CODEX_HOME/code-guard
npm ci --omit=optional --ignore-scripts --no-audit --no-fund
python3 -m unittest -v test_guard.py

cd /目标/CODEX_HOME/md-governance
python3 -m unittest -v test_md.py
```

源码包锁定 ESLint 10.15.0、TypeScript ESLint parser 8.73.0、TypeScript 6.0.3；以锁文件及接收机器实际测试为准。若版本不可取得，明确说明，升级后重验，不能静默换版本。

先测试候选安装，再合并注册 Hooks，检查配置能被当前 Codex 识别。通过应用支持的审阅入口让用户信任新 Hook；不伪造信任状态、不关闭信任机制，也不把手工调用脚本当成自动触发成功。

## 4. 本地代码门禁如何工作

Skill 保存操作方法；执行约束来自本地程序和已信任 Hooks。用户级安装可跨项目使用，检查器独立于项目自己的 ESLint 配置；它不保证其他应用、其他机器或其他用户也受到约束。

| Hook | 职责 |
|---|---|
| SessionStart | 提供入口信息，建立适用的初始状态 |
| PreToolUse | 在实际目标根目录建立或复用修改前基线 |
| PostToolUse | 同步检查编辑结果，违规反馈给 Agent 继续修复 |
| Stop / SubagentStop | 复查本会话登记的根目录，失败时要求继续处理 |

登记根目录必须通过工具明确的 `workdir`。不要在声明的目录之外用绝对路径或隐藏的 `cd` 写代码。独立登记的嵌套 Git 仓库使用自己的基线，父目录不重复将整仓旧代码当成新代码；结束前仍会检查子仓库新违规。

基线用于区分存量和本次增量，不要求先修完旧问题；新增及加重的违规失败；成功降低的指标不能随后回升。提交代码或换聊天不能消除失败。检查器缺失、运行失败及不支持的类型不能当作通过。

下表是此交接版本的核验快照，运行权威始终是 `scan.mjs` 和 `python_metrics.py`；不要再把数值复制成其他常驻指令的第二套规则。

| JS/TS 指标 | 默认上限 |
|---|---:|
| 文件有效行 | 500 |
| 函数有效行 | 80 |
| 函数语句数 | 50 |
| 圈复杂度 | 15 |
| 嵌套深度 | 4 |

JS/TS 行数忽略空行及注释。Python 实现提供 AST 行数与分支检查，不等于完整 ESLint 规则或同一复杂度定义。JS/TS/JSX/TSX 与 Python 已有适配；其他已识别语言在修改时阻断，未知扩展名不保证覆盖，需先补适配与独立测试。

检查器同时拒绝内联关闭检查，并拦已登记的废弃 API 和模块引用。依赖环境、Git 元数据及检查状态目录属于明确排除范围；修改后的符号链接不直接认证为已检查源码。

“过老实现”不能靠文件名、日期或 `legacy` 字样判断。先确认替代契约和调用方，补业务验证，迁移调用，禁止新增旧引用，最后删除可安全移除的实现。历史数据兼容职责必须保留或显式迁移。

项目专属的废弃模块登记在 `policies.json`；本次交付该清单为空，不能声称项目全部旧实现已被禁用。示例只是格式，必须替换为真实已确认的契约：

```json
{
  "retiredModules": [
    {
      "root": "/absolute/project",
      "module": "./old-conversion.js",
      "replacement": "./unit-conversion.js"
    }
  ]
}
```

该实现检查静态可解析的 require/import 引用，包括字面量动态 import；计算出来的模块路径不保证覆盖。检查正确依赖 AST 和实际语言语义，不用几个搜索关键词冒充通用分析器。

## 5. MD 文件只维护一份权威

| 文档 | 应放的内容 | 不应常驻的内容 |
|---|---|---|
| 全局 AGENTS | 跨项目偏好、授权边界、必要入口 | 某次任务的状态与历史流水 |
| 项目 AGENTS | 项目差异、启动及验证路由、项目边界 | 复述全局规则、旧分支状态 |
| 业务 Spec | 用户可观察行为、边界、独立例子 | 实现完成回执与部署推断 |
| Skill | 条件触发的复用方法 | 大量通用常识和重复数值 |
| 历史记录 | 决策、旧方案、验收证据 | 被当作当前任务或当前授权 |

清理时逐项判定保留、合并、引用、移动或归档。不能为了缩短文字取消已有授权、必要条件或业务例外；含义不明的高影响冲突先查用户依据，仍无法确定才询问。

每次新增先找所有者及现有近义条目；优先修改原条目。一个失败不自动变成全局永久禁令。能由代码、类型、测试或检查器保证的要求，优先留在程序里，入口只写如何调用。

按条件加载细节，而不是将长文拆成多个必须每次一起读的文件。根入口的字数下降只说明加载体积减少，不证明全部历史干净，更不代表精确 token 数下降了同样比例。

## 6. 每次写入指令的实际步骤

正式文件之外准备 `.stage` 草稿。下面的命令展示适配后的调用方式；默认安装对应工具在 `~/.codex/md-governance/md_write.py`：

```sh
python3 /目标/CODEX_HOME/md-governance/md_write.py analyze \
  --target /absolute/project/AGENTS.md \
  --draft /absolute/work/agents.stage
```

先修复结构检查结果，再对照原文、当前全局及领域权威进行语义审阅。检查器提供近似改写候选，但不理解所有语义；“找到相似文字”和“确实重复或冲突”必须区分。

审阅文件需要下列字段。哈希与新增条目 ID 来自分析结果，不手填猜测值；每个新增或重写条目有自己的来源与理由，不能用脚本批量填同一句“已检查”。

```json
{
  "target": "/absolute/project/AGENTS.md",
  "base_sha256": "分析结果中的原文哈希",
  "candidate_sha256": "分析结果中的草稿哈希",
  "basis": "本次明确需求和可靠依据",
  "ownership": "为何这个位置是唯一权威",
  "overlap": "与哪些现有条目比较，怎样避免重复",
  "conflicts": "核对了哪些规则及授权边界",
  "preservation": "保留的含义、例外与旧文去向",
  "clauses": [
    {
      "id": "分析结果中的某条新增条目ID",
      "source": "用户决定或可定位的原始规则",
      "reason": "本条新增或重写的具体必要性"
    }
  ]
}
```

```sh
python3 /目标/CODEX_HOME/md-governance/md_write.py apply \
  --target /absolute/project/AGENTS.md \
  --draft /absolute/work/agents.stage \
  --review /absolute/work/review.json
```

写入前再次检查原文和候选版本；版本变了，原审阅不能继续使用。结构和审阅有效后才原子替换正式文件。运行收据保存在私有状态目录，不塞进每轮上下文，也不等于独立人工批准。

先用受控写入接口审阅并安装接收方选用的 Skill 及 AGENTS 条件入口，再启用文档门禁；不要凭空生成一批收据来认证未审阅内容。

文档门禁覆盖活跃的 AGENTS、Skill、Spec、已登记权威及相应现行引用，排除历史归档和普通产物。既有文档可以作为初始存量记录，不要求接手时逐篇补审或清理；本次新写或修改不应通过改文件名、换聊天、删收据或转移目录绕过治理。

预算快照为 AGENTS 3000 字符、Skill 5000 字符、其他受控文档默认 10000 字符、单条 260 字符；实际值统一在 `md_rules.py`。按源代码核对具体覆盖及排除，不宣称任意 MD 都被全文理解。

需要保留的检查包括：预算、过长条目、同节重名、规范化重复、跨文件精确重复、本地文件链接、合并冲突标记、审阅完整性和版本失效。现行权威的未批准删除也需拦住；历史目录不因链接链重新变成当前规范。

## 7. 集成、性能和完整性

代码与文档检查共用现有 Hook 入口，不再注册另一组重复事件。候选文档写入接口可先独立验证，再接入编辑后与结束检查；保留其他插件的 Hooks 和任务原有行为。

安装完整性清单绑定接收机器上的执行文件和配置；源码包不携带发送方的 `integrity.json`。审阅后用目标绝对路径到 SHA-256 的 JSON 映射创建该文件，再验证修改会被发现。

至少绑定代码驱动、扫描器、Python 检查器、策略与依赖锁、四个文档组件脚本，以及最终 Hook 配置。先核实文件存在，生成清单后复核每个哈希；路径必须来自接收方安装目录。

当前参考实现允许首次安装时暂缺完整性清单；因此启用验收必须显式确认 `integrity.json` 已创建且有效，不能把文件缺失时的普通运行误报为完整性检查成功。

不得在普通任务里修改检查器或重算完整性清单来通过失败。显式升级检查器时，先保存旧版本、完成差异审阅和回归，再更新清单。该清单本身仍是本地文件，不是不可篡改的安全边界。

新加检查维度时，既有文件的初始登记须与新增违规分开；迁移只接纳可证实的原状，不能清空或放宽原有代码基线。保留这次登记的范围及验证记录，不拿“迁移”当消除失败的借口。

原子替换防止半写文件，不等于完整的跨进程并发事务；同一权威文档应串行维护，或另实现并验证相应文件锁。

查重为整批语料建立索引，避免每个文件反复比较所有文件。限制历史引用展开，缓存有效结果；性能优化不能通过漏查新文档、忽略子仓库或取消失败来实现。

## 8. 按需使用的工程 Skill

基础层仍由 `local-code-guard` 执行本地门禁、`instruction-maintenance` 管理持久指令。新增三种方法复用这些能力，不另造质量门禁或改部署权限。

- `project-verification`：复用项目已有启动和验证入口；只补当前关键路径，实际运行并保存结果及清理证据。单入口 CLI 不强制另建路由或功能地图，入口多且难以发现时才拆地图。
- `prevent-repeat-errors`：从已证实的重复错误选择模块边界、类型契约、现有检查或行为回归，证明错误被拒绝、合法路径通过；扫描对象缺失或数量为零必须失败，不能空扫描报成功。
- `evaluate-agent-skills`：用相同任务、初始文件、权限、模型和预算对照候选，先小样本诊断；根据波动和风险决定扩样。使用未参与调提示的任务检验泛化，报告成本，不凭空设提速百分比或运行次数。

复用与执行位置分开判断：轻量纯逻辑可进入共享模块；初始化开销和耗时工作需单独评估，必要时在后台执行并通过消息返回。不要因为禁止跨层导入而机械复制逻辑，也不假定导入后代码仍在原线程运行。

高风险业务以需求或独立例子定义答案，按角色、状态、数据归属、异常、重复与并发等维度挑代表场景；核对页面、真实保存和后续读取。代码与测试可能共享误解，截图或编译通过不能代替业务证据。

金额、库存、权限、删除及已修 Bug 优先保留有效回归；普通文案布局优先实际操作。不堆无意义测试，不把缺环境、跳过、未执行混成通过，也不靠改预期或删除断言修复业务失败。

## 9. 衡量整个闭环，而不只证明 Hook 能跑

分开报告门禁机制、Skill 效果和真实交付质量。两组都保留同一全局 Hook 时，只是在比较新增 Skill，不能称为“无闭环/有闭环”对照；共享状态干扰、已见任务复测和缺失成本数据都必须披露。

接入 CI 属于尚需按仓库适配的覆盖工作，本源码包未提供通用 CI 适配器。检查本地、其他机器、合并和发布入口；对可信 base 与候选 head 的新增/恶化违规设置门禁，并证明故意错误不能合入，不能直接空跑 Hook 事件脚本就宣布 CI 已接通。

效果统计记录首稿与最终业务结果、拦截、修复、误报、返工及耗时和 token 成本；全仓指标同时考虑功能量增长、违规占比与分位数。短期观察未改善不证明工具无效，指标增加也不等于由 Hook 导致恶化。

新增 Skill 的历史试验共 11 次独立任务执行，曾修复“没有源码仍报告通过”的具体问题；这是小样本诊断，不证明普遍提速。整合时再次复验发行检查 7 项、边界案例 8 项及指南案例 2 项，均通过；不将这些数字与基础门禁的历史 41 项简单相加为总体收益。

使用验证材料时保持其评估用途：进入 `validation/agent-engineering-skills/`，先运行 `python3 -m unittest discover -s tests -v`；再运行下列复验器。它们只针对随包的合成 Panel/Ledger，不是任意应用的通用驱动器。

```sh
python3 tools/check_boundary_submission.py evaluations/submissions/revised/panel
python3 tools/check_guide_submission.py evaluations/submissions/revised/ledger
```

## 10. 必须执行的验收

在独立、已登记的临时目录验证；使用合成数据，不碰真实业务记录。制造的违规是测试，失败后应修复或清理样例，不能修改阈值、清空基线或留下影响其他任务的失败状态。

### 代码与范围

| 场景 | 预期 |
|---|---|
| 新写 85 有效行函数 | 自动失败；缩短后通过 |
| 一行堆放过多语句 | 失败 |
| 加重旧违规 | 失败；降低后不能反弹 |
| 废弃 API、旧模块、关闭 lint | 失败 |
| 提交或换聊天 | 不消除失败 |
| 嵌套仓库 | 独立基线；新违规仍失败 |

### 指令与异常

| 场景 | 预期 |
|---|---|
| 重复且无审阅的 AGENTS | 自动失败 |
| 审阅后原文或草稿改变 | 过期审阅被拒绝 |
| 新条目缺来源或理由 | 不允许写入 |
| 无效草稿走 apply | 原文不变 |
| 文档未变但链接目标删除 | 发现断链 |
| 缺解释器或语言适配 | 报阻碍，不报通过 |

手工单测通过之后，还要观察真实 Codex 编辑工具触发失败、Agent 修复及再次自动放行。PostToolUse 不能撤销已发生的写入，所以不能说所有坏内容都无法保存；正常受控写入走草稿预检，直接写入则立即被检查并阻止完成。

普通编辑器红线、文件监听、Git 提交钩子和构建门禁可以作为补充，但这次交付没有证明它们已配置。不要把“Codex 工具调用后同步检查”说成任何编辑器逐键检查，也不要说本地机制无法被机器拥有者绕过。

## 11. 收尾交付与恢复

报告已安装和已启用的组件、实际覆盖、未覆盖语言、测试及真实触发证据、恢复点与完成提交。未运行、信任未完成、PR 未合并、真机未验收及部署未确认的状态必须分别写清。

恢复点必须在接收机器实际创建和核实；不能引用发送方的提交编号作为自己的恢复能力。已有未提交工作要另外保存完整快照，敏感文件不入 Git。


恢复时依据目标任务保存的版本，只处理本任务文件，保护后续及他人的修改。受控文档恢复也需按对应版本审阅；不能删除状态目录或盲目恢复全局配置。未合并或仍在使用的分支和工作区不清理。
